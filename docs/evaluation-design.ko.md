# 의사결정에 쓸 수 있는 평가 설계하기

[English](evaluation-design.en.md) · [Azure 없이 시작](offline.ko.md) · [내 실제 결과 읽기](validation.ko.md#read-your-results) · [호환성과 출처](compatibility.ko.md)

**판단할 일을 정하고, 실험 조건을 고정한 뒤, 개선과 회귀를 함께 확인합니다.** 높은 평균·HTTP 성공·Foundry 평가 완료가 운영 승인을 뜻하지 않습니다.

내 애플리케이션에 실습을 적용할 때 읽는 참고 문서입니다. 120분 기본 실습에 필수 단계를 추가하지 않습니다.

## 1. 모델 호출 전에 평가 계약 작성

| 정할 것 | 실습의 예 | 내 애플리케이션에 기록할 것 |
|---|---|---|
| 무엇을 평가하나? | 독립적인 규정 질문과 답변 한 쌍 | 한 턴, 전체 대화, 검색 단계, 도구 호출, 전체 업무 중 평가 단위 |
| 무엇은 반드시 맞아야 하나? | 판단·금액·출처·권한 범위 | 업무상 불변 조건과 위반 시 영향 |
| 무엇을 개선하나? | 지침 V1 → V2 | **의도한 변경 하나**와 가설 |
| 무엇을 고정하나? | 모델·dev·말뭉치·judge·평가기·동시성 | 버전·해시·실행 설정·입력 분포 |
| 무엇을 실패로 보나? | 오답, 누락·잘못된 근거, 호출 오류 | 품질 실패·서비스 실패·측정 누락을 구분 |
| 누가 결정하나? | 검토자가 사례를 설명하며 운영 승인은 내리지 않음 | 책임자·검토 절차·롤백 기준 |
| 얼마까지 사용할 수 있나? | 정해진 문항 수. 레벨 2·3은 별도 호출 | 호출·토큰·시간 예산과 중단 조건 |

**점수를 본 뒤 합격선을 고르지 않습니다.** 실습 업무 게이트는 모델별 80% 이상과 필수 인용 전부 유효, native 품질 기준은 1–5점 중 4점입니다. 이는 실습의 선택이지 Foundry의 보편적 기본값이나 모든 업무에 적합한 위험 허용치가 아닙니다.

## 2. 근거를 제공할 수 있는 지표 선택

| 알고 싶은 것 | 적합한 신호 | 필요한 근거 | 중요한 한계 |
|---|---|---|---|
| 답변이 검색 내용에 근거하나? | Groundedness | 답변·실제 검색 context. 질문도 도움이 됨 | 오래된 규정을 충실히 반복해도 업무에는 틀릴 수 있음 |
| 질문에 응답하나? | Relevance | 질문·답변 | 정당한 거절은 업무 맥락으로 해석해야 할 수 있음 |
| 업무 계약을 지키나? | 결정적 코드 검사 | 구조화된 판단·고정 정답·금액·인용 규칙 | 토큰·숫자의 존재가 전체 의미 정확성을 입증하지 않음 |
| 의도한 정책·권한을 지키나? | 검토한 도메인 rubric | 지침·기대 행동·정책 근거·답변 | judge도 편향되거나 미묘한 모순을 놓칠 수 있음 |
| 도구가 올바른 작업을 했나? | 도구 호출·과정 평가 | 실제 호출·인수·도구 결과·기대 행동 | 최종 답변 텍스트만으로 실제 실행을 증명할 수 없음 |
| 유해하거나 공격에 취약한가? | 안전 평가기·승인된 red teaming | 허가된 대상과 명시적인 위험 분류 | ASR은 품질 점수와 방향이 다르며 관측 실패 0건은 안전 증명이 아님 |
| 대화 전체가 성공했나? | 대화 단위 평가 | 순서가 있는 전체 턴·상태·행동·최종 결과 | 턴별 점수 평균이 전체 대화 성공은 아님 |

**이 저장소가 구현하는 범위:** 레벨 1 업무 검사·groundedness·relevance, 레벨 2 사용자 지정 코드·rubric·추가 기본 평가기, 레벨 3 생성 rubric·합성 스트레스 테스트·모델 red team·에이전트 직접 호출·trace·일정 기반 평가입니다.

**범용 멀티턴·멀티모달·도구 실행 경로 벤치마크는 구현하지 않습니다.** 레벨 3 red team의 대상은 V2 지침 없는 모델이며 전체 RAG 에이전트가 아닙니다. 다른 평가 단위는 [공식 워크플로 표](https://learn.microsoft.com/azure/foundry/observability/how-to/cloud-evaluation#choose-your-starting-point)를 따릅니다.

### API 계열과 출력 형태를 섞지 않기

실제 실행 경로는 classic 로컬 `azure.ai.evaluation.evaluate()`가 아니라 `AIProjectClient.get_openai_client().evals`입니다. 저장된 응답은 `{{item...}}`에서 매핑합니다. 대상이 새로 생성하는 평가에는 평가기에 따라 `{{sample.output_text}}` 또는 전체 `{{sample.output_items}}`도 사용합니다.

레벨 1의 `response`는 저장된 **answer 텍스트**, `context`는 실제 검색 결과이며, `ground_truth`는 **두 native 평가기에 매핑하지 않습니다.** `decision`·`citations`는 코드 평가가 별도로 검사합니다. “groundedness”를 고른다고 구조화된 필드까지 자동 검증되지는 않습니다. [정확한 입력 표](validation.ko.md#business-checks)와 [현재 SDK 안내](https://learn.microsoft.com/azure/foundry/observability/how-to/cloud-evaluation-datasets)를 참고합니다.

## 3. 데이터셋 카드: 수치가 대표하는 범위

| 항목 | 실제 클라우드 실습 | 오프라인 입문 |
|---|---|---|
| 출처 | 직접 작성한 합성 회사 규정·질문 | 직접 작성한 합성 식비 규정·답변·정답표 |
| 제공 텍스트의 개인정보·고객 데이터 | 포함을 의도하지 않았으며 운영 trace는 제공하지 않음 | 없음. 네트워크 데이터도 사용하지 않음 |
| 언어 | 한국어·영어를 별도 집단으로 실행 | 한국어·영어 별도 예제 |
| 규정 문서 | 언어별 7개 | 언어별 별도의 교육용 규정 1개 |
| 개발 세트 | 언어별 6문항 | 8문항 전부 교육용 |
| Holdout | 언어별 4문항. V2 고정 후에만 확인 | **없음**. 일반화 검증이 아님 |
| 관측값 | V1 dev 18 + V2 dev 18 + 고정 V2 holdout 12응답 | 작성된 답변 8쌍. **모델 호출 16회가 아님** |
| 이력 | 데이터·말뭉치·지침 해시, 모델 버전, run·trace ID | 입력 SHA-256과 `synthetic_offline_demonstration` 표시 |
| 라벨의 의미 | 고정 사례 정답과 실제 검토 기록 | 제공된 `human_reference_*` 정답표. 새 사람 검토가 아님 |
| 가능한 결론 | 이 고정 사례에서 관찰한 행동 | 평가 동작의 이해 |
| 불가능한 결론 | 운영 신뢰도·일반적인 모델 순위 | 모델 성능·실제 클라우드 성공·운영 승인 |

본실습 데이터는 `data/`·`data/en/`, 오프라인 예제는 `data/offline/`에 있습니다. **Holdout 답변을 미리 보거나 지침 개발 데이터로 복사하지 않습니다.** `feedback`은 holdout 수집을 거부합니다. 공개된 교육용 holdout은 비공개 운영 테스트가 아니며 학습 데이터 오염 방지를 입증할 수 없습니다.

### 실제 업무를 대표하는 데이터 만들기

사용이 허용된 비식별 트래픽과 전문가가 작성한 경계 사례에서 시작합니다. 출처·이력, 시나리오 계열, 언어, 심각도, 정책 적용일, 기대 행동, 검토자, split을 남깁니다. 쉬운 질문만 넣지 말고 근거 부족·오래되거나 상충하는 문서·금액 경계·정당한 거절·권한 밖 작업을 포함합니다.

행 번호만으로 나누지 않고 업무에 맞게 **대화·문서·시나리오 계열·기간** 단위로 분리합니다. 같은 상황을 바꿔 쓴 질문이 dev·holdout에 나뉘면 누수가 생깁니다. 중요·소수 집단을 따로 보고하여 쉬운 다수 사례가 영향이 큰 소수 실패를 가리지 않게 합니다.

생성한 질문과 라벨은 사람이 검토한 뒤 정답으로 사용합니다. 평가 대상 시스템을 유일한 정답 작성자로 삼지 않습니다. 어려운 사례를 삭제하는 대신 데이터 변경을 버전으로 남기고, 기존 holdout이 개선에 쓰였다면 새로운 최종 검증 세트를 확보합니다.

## 4. Judge를 검증하고 맹신하지 않기

실제 `calibrate` 단계는 근거 있는 답변 한 개와 없는 답변 한 개를 확인합니다. **두 예제는 동작 확인이지 judge의 통계적 검증이 아닙니다.**

실무에는 명확한 통과·실패, 경계 판단, 정당한 거절, 영향이 큰 사례를 포함한 별도 검토 세트를 만듭니다. 모델과 독립적으로 검토자가 불일치를 조정하고 두 오류를 모두 봅니다.

- **잘못된 통과:** 허용하면 안 되는 답을 judge가 통과시킴.
- **잘못된 실패:** 허용 가능한 답을 judge가 실패시킴.

언어·시나리오·위험별로 나눕니다. 영향이 큰 업무는 여러 적격 검토자나 judge와 대조합니다. 실험 중에는 judge 배포·버전·rubric·기준값·입력 매핑을 고정합니다. 일치도가 낮으면 rubric과 입력을 검토하지, 사람의 정답을 자동으로 바꾸지 않습니다.

레벨 2는 코드와 rubric 판정을 비교하고 한 조건에서는 의도적으로 근거를 제거합니다. 결정적 검사도 LLM judge도 절대적인 정답 기준은 아닙니다. 오프라인 `O05`에서 코드 평가기의 사각지대를 직접 실행해 확인할 수 있습니다.

## 5. 같은 사례를 짝지어 평균에 가려진 회귀 확인

`compare`는 dev 실행을 `(model_key, case_id)`로 짝지어 **양방향 변화**를 저장합니다. 파일 순서는 무관하며 중복·누락 쌍을 거부합니다. 요청한 순서의 첫 dev label을 기준으로 이후 dev label을 비교하고, 서로 다른 질문인 holdout과 dev는 짝짓지 않습니다.

이전에 저장한 비교도 계속 읽을 수 있습니다. 새 진단을 추가하려면 실제 사용한 같은 label로 `compare`만 다시 실행하며 수집이나 judge 호출은 반복하지 않습니다.

기존 [7단계 비교](../README.ko.md#compare-results) 뒤 `comparison.json → paired_comparisons`와 `summary`의 추가 줄을 읽습니다.

| 필드 | 의미 |
|---|---|
| `fail_to_pass`, `improved_case_ids` | 이전 실패에서 통과로 바뀐 사례 |
| `pass_to_fail`, `regressed_case_ids` | 이전 통과에서 실패로 바뀐 사례 |
| `both_pass`, `both_fail` | 통과·실패 여부가 유지된 사례 |
| `context_changed_case_ids` | 두 응답 사이의 검색 텍스트가 다른 사례 |
| `pass_rate_delta` | `(fail_to_pass - pass_to_fail) / total`인 기술적 차이 |

**순변화가 좋아도 회귀는 반드시 검토합니다.** 검색 근거가 달라졌다면 전체 시스템 관측값이며 지침·모델만이 차이의 원인이라는 증거는 아닙니다. 근거가 같다는 것만으로 인과관계가 입증되는 것도 아닙니다.

추가된 값은 진단 정보입니다. 기존 레벨 1·3 게이트의 합격선을 **몰래 바꾸지 않습니다.** 운영 정책이 중요 사례의 회귀를 허용하지 않는다면 별도의 명시적·검토된 게이트로 만듭니다. 오프라인의 `--fail-on-regression`은 그 차이를 보여 줍니다.

## 6. 4건 통과는 신뢰도 100%가 아님

모델별 요약에는 `business_pass_rate_wilson_95.lower`·`.upper`가 있고, `summary`에는 **예시적 양측 95% Wilson 구간**으로 표시됩니다.

**4/4** 통과의 구간은 약 **51.0%–100.0%**이며, 실제 성공 확률이 100%라는 증거가 아닙니다. 구현은 [`wilson_interval()`](../scripts/grading.py), 방법 참고는 [Wilson score interval](https://www.statsmodels.org/stable/generated/statsmodels.stats.proportion.proportion_confint.html)입니다.

**공식보다 전제가 중요합니다.** 이항 계산은 일정한 성공 확률에서 나온 독립 시행을 가정합니다. 이 실습은 적고 의도적으로 고른 사례로 이루어져 운영의 대표 표본이 아닙니다. 따라서 구간은 표본 크기의 불확실성을 설명하는 도구이지 보정된 운영 보증이 아닙니다.

같은 4문항에 대한 세 모델의 답을 한 모델의 독립 관측 12개로 합치지 않습니다. 번역이나 같은 답을 반복 채점한 값을 합쳐 분모를 부풀리지 않습니다. 구간의 중첩 여부는 짝지은 유의성 검정이 아닙니다.

운영 실험에는 표본 수·시나리오 범위·반복 횟수·예산·분석법을 미리 정합니다. 반복 실행으로 확률적 변동을 보되 독립 시나리오 단위나 타당한 군집 분석을 사용합니다. 이 저장소는 차이의 bootstrap 신뢰구간이나 자동 유의성 판정을 구현하지 않습니다.

## 7. 지침 수정 전에 실패 분류

| 업무 검사 | Native 점수 | 먼저 확인할 것 |
|---|---|---|
| 통과 | 통과 | 남은 의미·정책 적용일·안전·권한 문제, 작은 표본의 한계 |
| 실패 | 통과 | 유창한 본문과 별개인 구조화된 판단·인용 계약 |
| 통과 | 실패 | 코드 사각지대, 정당한 거절, judge 입력·근거·rubric 적합성 |
| 실패 | 실패 | 검색 근거·정책 선택·답변 생성·평가기 매핑 |

HTTP 오류·평가 행 누락·잘못된 점수·timeout·trace 누락은 **증거 미완료**이지 0점이나 성공이 아닙니다. 실패 시도를 보존합니다. 지원되는 경로에서는 같은 원격 run을 조회·재개하며, 낮은 유효 점수를 통과할 때까지 재실행하지 않습니다.

실제 trace로 검색·모델·출력 형식·도구·평가기 실패를 구분합니다. 원인 하나를 고치고 같은 dev·평가기 정의로 비교한 뒤, 후보를 고정하고 holdout을 봅니다.

## 8. 비용·개인정보·책임 있는 릴리스 경계

예산은 **대상 모델 + 검색 planner/Search + judge + hosted compute + 로그/저장소**로 나누어 잡습니다. 18응답씩 두 label에 native 평가기 두 개면 72개의 행·평가기 판정입니다. 이는 계획용 수량이지 **정확히 72회의 유료 API 호출이라는 보장이 아닙니다.** 재시도·서비스 실행 방식·calibration·추가 레벨에 따라 사용량이 달라집니다.

관측한 토큰에 해당 배포의 현재 입력·캐시 입력·출력 단가를 적용합니다. 가격·사용량이 없으면 미확인으로 두지 `$0`으로 채우지 않습니다. native 모델 대상 추정 비용도 일부만 산정될 수 있으며 전체 Azure 청구액이 아닙니다. [공식 비용 한계](https://learn.microsoft.com/azure/foundry/observability/how-to/cloud-evaluation-results#review-model-target-latency-and-estimated-cost)와 [실습 측정 범위](validation.ko.md#tradeoffs)를 봅니다.

실제 데이터에는 **데이터와 전송 대상 모두에 대한 승인**을 받고, 비식별화한 뒤 리전·네트워크·저장소·보존 기간·접근 권한을 정합니다. `.gitignore`는 우발적 Git 추가 방지이지 암호화나 데이터 유출 방지 시스템이 아닙니다. `.env`·원본 trace·평가 결과·식별자가 있는 화면을 공개하지 않습니다. 연속 평가는 무료 최종 검사가 아니라 지속적인 데이터 처리와 비용입니다.

릴리스에는 품질·안전 신호, 미검증 범위, 운영 비용·지연 예산, 사람의 승인, 모니터링·알림 책임자, 롤백 방법, 다음 검토일을 기록합니다. 이 실습의 `production_release_approved`는 항상 false입니다.
